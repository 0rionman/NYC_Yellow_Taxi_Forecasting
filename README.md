# NYC Yellow Taxi — почасовой прогноз, версия 2

Исследовательский проект для Google Colab с приложением Streamlit. Прогнозирует число
очищенных поездок с посадкой за следующий локальный час суммарно по пяти боро Нью-Йорка.
Источник: [NYC TLC](https://www.nyc.gov/site/tlc/about/tlc-trip-record-data.page).

## Быстрый запуск: Google Colab

[Открыть ноутбук в Colab](https://colab.research.google.com/github/0rionman/NYC_Yellow_Taxi_Forecasting/blob/main/NYC_Taxi_v2_Colab.ipynb)

1. Загрузите **NYC_Taxi_v2_Colab.ipynb** в Colab, выберите CPU.
2. Проверьте настройки: год 2024, январь 2025 как новый holdout, штрафы 3/1,
   критерий выбора `MAE` или `BusinessLossPerHour`.
3. Выполните ячейки сверху вниз. Зависимости устанавливаются в отдельный venv,
   не изменяя базовые pandas/NumPy/requests Colab. Проверяется `pip check`.
4. Ноутбук последовательно скачивает 12 или 13 файлов, удаляя сырые файлы после агрегации.
   Кэш сохраняет правила очистки и контрольные суммы. Длительность зависит от сети и CPU.
5. После обучения скачайте ZIP проекта с папкой `artifacts`, моделью и результатами.
6. При желании включите последнюю ячейку Streamlit. В Colab используется встроенный iframe-прокси;
   это сеансовый просмотр, не публичное развёртывание. Если браузер блокирует прокси,
   запустите скачанный проект локально по инструкции ниже.

Синтетические тесты запускаются до скачивания данных. Их числа не попадают в отчёт модели.
Ноутбук содержит исходники проекта внутри себя, отдельно загружать архив не нужно.

## Локальное приложение

Требуется Python 3.11–3.13. Из каталога проекта:

```text
python -m venv .venv
```

Windows PowerShell:

```powershell
.venv\Scripts\python.exe -m pip install --no-cache-dir -r requirements.lock.txt
.venv\Scripts\python.exe -m pip check
.venv\Scripts\python.exe -m streamlit run app.py
```

Linux/macOS:

```sh
.venv/bin/python -m pip install --no-cache-dir -r requirements.lock.txt
.venv/bin/python -m pip check
.venv/bin/python -m streamlit run app.py
```

Откройте [локальное приложение](http://localhost:8501). Рядом с `app.py` должна находиться
папка `artifacts`, скачанная после обучения. Без артефактов приложение показывает инструкцию,
а не вымышленные результаты. Используйте `model.joblib` только из собственного доверенного запуска.

## Docker

```sh
docker compose up --build
```

Порт доступен только локально: `127.0.0.1:8501`. Папка `artifacts` подключена для чтения.
Контейнер запускается от непривилегированного пользователя, имеет healthcheck.
Базовый Python — 3.13, как в предоставленном запуске Colab. Если обучение выполнено на другой версии,
передайте её через `docker compose build --build-arg PYTHON_VERSION=3.11` (или нужную версию).
При наличии `requirements.lock.txt` из обучения Docker устанавливает именно его.
Сборка и HTTP-healthcheck включены в GitHub Actions. Их наличие не означает,
что Docker уже был проверен в среде автора — см. `VALIDATION.md`.

## Исследовательский протокол

- 2024: январь–июль и расширяющаяся история для внешних фолдов август/сентябрь/октябрь.
- Внутри каждого фолда последние 14 дней перед внешним месяцем выделены для калибровки;
  предыдущие 14 — для ранней остановки LightGBM. После выбора числа деревьев модель
  переобучается на доступной истории до внутренней калибровки.
- Optuna отдельно подбирает Ridge и LightGBM. WeeklyNaive сравнивается на тех же строках.
- Три набора признаков: календарь; календарь+лаги; календарь+лаги+окна.
  Стандартный `month` и константная `zone` исключены: первый не подтверждает годовую
  сезонность на одном году, вторая не несёт информации в городской задаче.
- По CV фиксируются семейство, признаки и способ интервала: абсолютная ошибка либо
  ошибка, нормированная на sqrt прогноза. Выбирается ближайшее к номиналу покрытие,
  при равенстве — меньшая ширина. Гарантия покрытия не заявляется.
- Финальное обучение — январь–октябрь с параметрами CV; ноябрь — отдельная калибровка.
- Декабрь 2024 уже изучен и называется `December_seen`.
- Январь 2025 называется `January_new`: независим только при первом замороженном протоколе,
  если его не использовали ранее. Последующая подгонка по его результатам лишает его этого статуса.

Фолды задаются календарными границами, а не случайным KFold. Признаки причинные:
лаг и каждое окно используют только прошлое с заданной задержкой доступности.
Пропуски после DST не интерполируются для модели. Вход включает всю часовую сетку.

## Бизнес-ошибка

```text
Business Loss = sum(max(0, y - prediction) * COST_UNDERESTIMATION
                  + max(0, prediction - y) * COST_OVERESTIMATION)
```

В `config.json` параметры называются `cost_underestimation` и `cost_overestimation`;
по запросу пользователя начальные значения равны 3 и 1. Это **сценарные штрафы**.
Денежные потери автопарка не измерены. В Streamlit можно менять штрафы и видеть
пересчитанную бизнес-ошибку выбранной модели без переобучения.

`selection_metric="MAE"` — подбор по обычной ошибке.
`selection_metric="BusinessLossPerHour"` — подбор по асимметричной ошибке;
LightGBM использует quantile objective с alpha = cost_under / (cost_under + cost_over),
то есть 0.75 при штрафах 3/1. После обучения сохраняются обе группы метрик.

**Конкретная стоимость ошибки зависит от юнит-экономики автопарка; модель демонстрирует
возможность оптимизации под асимметричные штрафы (undersupply penalization).**
Нужны данные о длительности поездок и загрузке, чтобы переводить прогноз поездок в число машин.
Допустимый MAE и бизнес-назначение оставлены незаданными до согласования с заказчиком.

## Тестирование

```sh
python -m pytest -q
```

Тесты покрывают причинность признаков, задержки 1/2/24 часа, очистку Parquet,
инвалидацию кэша, пропуски/дубликаты/DST, устаревшую историю, сценарную стоимость,
сохранение/загрузку модели, полный искусственный эксперимент и Streamlit AppTest.
Это проверка реализации, не оценка качества на настоящих TLC данных.
В поставке: 23 теста успешно пройдены в чистой среде Python 3.11;
`pip check` не обнаружил несовместимых зависимостей. Локальные протоколы проверки включены в ZIP поставки; диагностические логи не публикуются в GitHub. Тесты на Python 3.11/3.13, Docker build и HTTP-healthcheck успешно прошли в [GitHub Actions](https://github.com/0rionman/NYC_Yellow_Taxi_Forecasting/actions/runs/35235805827).

## Обучение без ноутбука

```sh
python -m taxi_project.cli prepare --config config.json
python -m taxi_project.cli eda --config config.json
python -m taxi_project.cli train --config config.json
```

Для нового прогноза вызовите `load_model("artifacts/model.joblib")`, затем
`model.forecast(history, target_time="2025-02-01 00:00:00", live=False)`.
История: два столбца `pickup_hour`, `trips_count`; полный ряд неотрицательных значений,
последний час должен совпадать с целевым временем минус настроенная задержка.
`live=True` дополнительно проверяет текущий час Нью-Йорка. Исторический режим не проверяет
текущее календарное время, но всё равно проверяет согласованность истории с целевым часом.

## Ограничения и эксплуатация

- Итоговая стоимость и дистанция доступны после завершения поездки. Параметр задержки
  — сценарное предположение; готовность признаков онлайн не подтверждена реальным источником.
- TLC — исторический источник, не поток заказов. Прогноз не учитывает неудовлетворённый спрос.
- DST-часы и затронутые окна исключаются; число строк калибровки уменьшается.
- Только один год разработки, нет погоды/городских событий; годовая устойчивость не доказана.
- PSI >0.2 и покрытие <85% — диагностические ориентиры. Реальные SLA не придуманы.
  Мониторинг сейчас запускается вместе с оценкой и показывается в Streamlit, а не работает
  круглосуточно. Для эксплуатации нужен планировщик и накопление новых фактов.
- После изменения по результатам January_new нужен следующий неиспользованный holdout.
